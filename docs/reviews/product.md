# Product review: simplify the system around the consultation

Reviewed 13 September 2026. Source repository: `personal-ai-consulting-group-godaddy`, checkout commit `49c7ad9a0b3033e9437e79cd98ed5d35e71cfced`. All file and line references below refer to that source checkout, not this new repository. The review inspected current documents and source code; it did not reproduce production incidents or perform a live accessibility audit. No original files were changed.

## Recommendation

Replace the messenger and its connection workflows with one private, mobile-first browser application: sign in, open a consultation, describe the decision, see substantive consultant exchanges and evidence, then receive one practical recommendation. Keep the underlying consultation capabilities, exact model configuration and private-owner boundary. Simplify how the work is orchestrated and presented before adding anything new.

The largest product problem is a mismatch between the promised experience and the mechanism used to create it. The brief promises a real discussion, live research when needed, little technical noise and a useful decision (`docs/product-idea.md:45–76,132–155,215`). The current orchestration foregrounds repeated proposal reviews, deterministic operational notices and multiple configuration surfaces. This is observed code structure; its contribution to the user's frustration is a reasoned diagnosis, not a measured causal attribution for every outage.

**Simplify without revoking capabilities:** optional model preferences rather than setup prerequisites; history as a lightweight conversation list rather than a dashboard; one concise recovery state with preserved input; research available to the team as part of ordinary consultation; explicit but concise agreement when it matters; short messages written by agents rather than a UI that truncates long messages afterward.

## Minimum usable browser workflow

1. **Sign in.** One owner sign-in action. Returning owners arrive directly in their current or most recent consultation. A first-use data-processing explanation is concise and appears once; Google identity does not itself authorize providers to process the conversation.
2. **Start or resume a consultation.** A conversation list and New consultation are easy to reach. The empty state focuses on one input: “What do you need to decide?” Text, image/PDF attachment and any reconciled existing voice capability belong beside that input, not in settings.
3. **Provide only material clarification.** Head asks one specific question if it changes the recommendation. Answer normally, use the suggested answer or continue with an explicit assumption. Do not make every consultation complete a form.
4. **Follow and steer the discussion.** See real role-labelled messages and clear addressed replies. A small participant strip can show who is involved. Add information without opening a competing task. Stop is always accessible during work. New confirmed contributions arrive in the same view without reloads or opening tabs.
5. **Inspect evidence when needed.** Relevant claims link to their sources, with publication/access information when available. A source detail sheet can show what was checked; it must not imply that clicking a citation is needed to understand the recommendation. Unverified claims remain labelled.
6. **Act on the conclusion.** Head gives one recommendation, up to three concrete next actions, key risk and a condition for revisiting it. Actual disagreements are explicit. Follow-up continues with the same context; whole-conversation export/delete are secondary actions.
7. **Recover clearly.** If a provider is unavailable, show a short reason, preserve all accepted input and show the one applicable next action. Ordinary reconnection is automatic where safe. A required provider reauthentication remains exceptional; the new brief must not promise that revocable credentials can never expire.

Peer review agreement: genuine revoked authorization appears beside the paused consultation as “ChatGPT needs you to sign in again” with one “Reconnect ChatGPT” action, returning to the same consultation. Name Claude only when the selected Critic route needs it; an inactive provider remains silent. A quota limit shows known reset/retry information, while a transient outage shows its own retry state. Do not send the owner through a generic provider setup dashboard for either case. The exact supported reauthorization flow remains to be verified during implementation.

Mobile acceptance should cover a narrow viewport first: one reading column, stable composer, no horizontal page scrolling, practical tap targets, readable tables, sources and history in sheets/drawers, keyboard-safe composition and restored scroll position. Larger screens may reveal navigation beside the conversation. These are proposed design requirements, not verified properties of a built app.

## Conversation contract for the prototype

Prototype exchanges must be visibly identified as illustrative. They should demonstrate specific questions and revisions, not scripted applause or contrived disagreement. For example, using fictional figures:

> **Strategy Consultant → Financial Consultant:** The shorter trial limits commitment, but the recommendation depends on whether support fits within the fee. What delivery-cost threshold would change your view?
>
> **Financial Consultant → Strategy Consultant:** With the stated assumptions, the trial works only below eight delivery hours. I would include support time in that total and measure it in week one.
>
> **Critic → Financial Consultant:** Eight hours excludes preparation in your calculation. Include it before recommending the trial; otherwise the owner may accept work that already exceeds the threshold.
>
> **Financial Consultant → Critic:** Agreed. Including two hours of preparation leaves six delivery hours. I have changed the proposed cap and the stop condition.

The value is the corrected assumption and changed recommendation. Short acknowledgements can be appropriate when something was actually resolved. They should not substitute for the underlying reasoning, evidence or revision. No model's hidden chain of thought is part of this requirement.

## Verification needed before implementation

- **Owner/design review:** demonstrate sign-in → new question → focused clarification → live debate → sources → final → follow-up on mobile and desktop. Success means the owner can understand what changed in the discussion and act on the conclusion without visiting a connection screen.
- **Current settings preservation:** obtain a content-free effective-settings snapshot from the existing system. Do not mistake repository defaults or model labels in old design fixtures for the live selection. Record provider, model ID, effort and orchestration speed, including inactive Critic branch preferences if they are to remain available.
- **Capability reconciliation:** establish whether voice is an adopted later capability; preserve it if confirmed. Record any other disagreement between old brief and implemented behavior instead of using “simplify” to silently remove it.
- **Future implementation proof:** test real cited research, separate agent calls, a Critic challenge and changed response, persisted messages after browser reconnect, Stop, and an unavailable-provider state. A polished prototype cannot prove these backend capabilities.

This report is a source-backed product/code review and a replacement design recommendation. Production fault frequency, live provider readiness, effective deployed model settings and actual cross-device usability remain unverified by this reviewer.

## Resolved architecture challenge

Architecture Reviewer proposed one durable run record and one ordered append-only event stream in MySQL. Input acceptance and run advancement share a transaction with a client idempotency key; completed role responses and their next step commit atomically. A worker lease coordinates work, and a run generation blocks late commits after Stop. The browser reads/replays canonical events from its last sequence through SSE or incremental polling, so a separate browser-delivery outbox is unnecessary. Restart resumes the last committed step. A provider call completed outside the database transaction may have to repeat; the guarantee is one confirmed visible response per step, not exactly-once model execution.

Product Reviewer agrees that this preserves the needed experience while removing Matrix ingress/ACK/device delivery machinery. It is a reviewed design proposal, not implemented or tested behavior. Both reviewers agree that a useful outcome may include explicit disagreement; only actual current agreement is called consensus.
